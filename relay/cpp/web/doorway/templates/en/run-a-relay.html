Run your own R2R relay

Every R2R relay is the same single binary, with SQLite and OpenSSL compiled in. There is nothing to install first: no PHP, no Python, no Node, no database server, no web server. It runs on any Linux, x86-64 or ARM64 (a Raspberry Pi 4 or 5 is enough). Open ports 8787 and 8788, run one command as root, and your server is part of the network.

Where to run it: on the server itself. Rent a VPS (or use any always-on Linux box), log in to it over SSH as root or as any user with sudo, and paste the commands there. Nothing runs on your own computer.

A relay is also the way in when nobody can invite you. On first start it mints five invite codes of its own: claim one in the wallet, give the others to friends, and mint more whenever you like. From then on you are the one handing out invites, and each person you bring in gets three codes to pass on. Your invite codes below says where to find them.

Install — one command, on the server

curl -sSLO {{SCHEME}}://{{HOST}}/assets/r2r-relay-$(uname -m) && \
curl -sSLO {{SCHEME}}://{{HOST}}/assets/install.sh && \
curl -sSLO {{SCHEME}}://{{HOST}}/assets/setup-tls.sh && \
curl -sSLO {{SCHEME}}://{{HOST}}/assets/r2r-relay.service && \
chmod +x r2r-relay-* install.sh setup-tls.sh && \
sudo ./install.sh YOUR.SERVER.IP:8787
Replace YOUR.SERVER.IP with the public IP of the server you are typing this on — the one the relay will run on, not your laptop's. It is the address other relays will dial (curl -4 ifconfig.me on the server prints it). Leaving the placeholder unreplaced is the single most common install mistake.

Verify the download first

{{SCHEME}}://{{HOST}}/assets/ publishes the SHA-256 of every file it serves:

curl -s {{SCHEME}}://{{HOST}}/assets/ | grep -A2 "\"r2r-relay-$(uname -m)\""
sha256sum r2r-relay-*

What the installer does

It creates the r2r service user, installs the binary to /usr/local/bin/r2r-relay, lays out /etc/r2r and /var/lib/r2r, issues a self-signed TLS certificate, and enables a sandboxed systemd unit (ProtectSystem=strict, no capabilities, write access to /var/lib/r2r only). If something else is already listening on port 8787, the installer stops it and prints what it was, but does not touch its data.

Requirements & ports

Any Linux server on x86-64 or ARM64 — a cheap VPS, a Raspberry Pi 4 or 5, an Apple-silicon VM, an Ampere or Graviton instance — with root access and two open inbound ports. The binary is fully static, so no particular distribution or version is required; 32-bit ARM and RISC-V builds are published too. The relay is a single binary with an embedded SQLite database.

Port Protocol Who needs to reach it
8787ws:// + HTTPother relays, and clients on trusted networks
8788wss:// (TLS)remote clients connecting directly

Both must be open inbound. Nothing else is required — no nginx, no reverse proxy, no database server.

A domain name is optional. Relays authenticate each other with ed25519 signatures, not certificates, so a bare IP with the self-signed certificate is a fully functioning node. A domain plus a real certificate is only needed if browsers will connect directly to this relay — see TLS certificates.

Check that it works

systemctl status r2r-relay

Good output: active (running).

curl -s http://127.0.0.1:8787/status.json

Good output: JSON with uptime, peers, and payload counts.

r2r-probe --url ws://127.0.0.1:8787 ping

Good output: pong and a millisecond RTT.

Within a minute or two the node discovers other relays via gossip:

curl -s http://127.0.0.1:8787/peers.json | grep -c '"verified": true'

Good output: any number ≥ 1.

The relay also serves a human-readable status page at http://YOUR.SERVER.IP:8787/ — active nodes, uptime, payloads held, frames relayed — so you can point a browser at your own node.

Your invite codes

Registration on a relay is closed by default and works by invite code. On first start the relay mints five genesis codes into /var/lib/r2r/genesis-invites.txt (mode 0600, deliberately never written to the log). Each code (R2R-XXXX-XXXX-XXXX, with your IP folded in when you advertise one) works once. Claiming one registers an identity and gives that person three codes of their own, which unlock once they have actually used the network: received a few messages and chatted with whoever invited them. An identity registers only once per relay, so the network grows person-to-person, and every branch stays revocable.

sudo cat /var/lib/r2r/genesis-invites.txt
r2r-relay --mint-invites 10        # mint more at any time
A used invite code stores no personal data. Only the code, timestamps and the pseudonymous fingerprints of who issued and who claimed it — no name, no email, no phone number. An operator who wants a fully open relay can set --open-registration (or the equivalent in /etc/r2r/relay.env); identities are still recorded and newcomers still receive three (locked) codes, so clients behave identically either way.

Administering your relay

Day-to-day administration happens from your own wallet, not over SSH — the server-side CLI exists for setup and for operators who prefer the shell.

a) From your wallet — the owner panel

There is no admin key or password. The wallet already proves an ed25519 identity on every connection, so the relay simply keeps a list of identities allowed to administer it. Once, on the server:

sudo r2r-relay --owner-add R2R_YOUR_ADDRESS
sudo r2r-relay --list-owners
sudo r2r-relay --owner-remove YOUR-64-CHARACTER-FINGERPRINT   # revoke

Paste the R2R_… address the wallet shows in Settings — the same identity you already message with (the 64-character fingerprint works too). From the next connection the owner panel appears automatically in the wallet, and from it you can list accounts (usage, quota, pending messages, online state), change any account's storage allowance, and mint invite codes from your phone instead of reading a file over SSH.

There is no shared secret at all. Nothing to paste, nothing to leak, and revoking access is one command.

b) From the shell

Safe to run while the relay is live — the database is in WAL mode; no restart needed:

r2r-relay --set-quota FINGERPRINT 250    # give this user 250 MB
r2r-relay --list-quotas                  # every individual allowance
r2r-relay --clear-quota FINGERPRINT     # back to the relay default
r2r-relay --mint-invites 10

Every identity gets 1 MB by default; the allowance covers messages, voice/video recordings and encrypted history together. Going over it refuses new payloads — nothing already stored is ever deleted by a quota change, so lowering one is safe.

c) Settings reference

Full list from r2r-relay --help. Every flag has an R2R_* environment equivalent, set in /etc/r2r/relay.env:

Variable Meaning
R2R_ADVERTISEhost:port other relays dial. Without it, nobody can route to you.
R2R_SEEDSExtra relays to bootstrap from, host:port,host:port — added to the seed compiled into the binary.
DEFAULT_QUOTA_MBStorage each identity gets (default 1).
QUEUE_TTL_DAYS / BLOB_TTL_DAYSRetention; the longer of the two wins (default 7 days).
TURN_URL / TURN_USER / TURN_PASSNeeded for calls to connect through strict NATs.
R2R_ASSETS_DIRPublish a directory at /assets/ — turns the relay into a verified download mirror.

TLS certificates

  1. The self-signed certificate from the installer is genuinely enough for the relay network. Relays never check each other's certificate chains — they authenticate with an ed25519 signature pinned per address, which binds the node rather than a hostname and is stronger than a certificate for that job.
  2. A browser-trusted certificate is needed for exactly one thing: a browser that opened the wallet over HTTPS connecting straight to this relay. If users open the wallet as a local file (file://), plain ws:// to a bare IP works fine and this relay doesn't need a real cert. If you want one, point a DNS name at the node and run (port 80 must be reachable): 
    ./setup-tls.sh relay1.example.org
    Renewal never restarts the relay — the hook sends SIGHUP, the certificate is re-read in place, and no client connection or peer link drops.
  3. The private key is unreadable to your login shell on purpose. /etc/r2r/tls/key.pem is 0640 root:r2r.
    The fix is not to copy the key somewhere more permissive. Start the relay through systemd, or point --cert/--key at a throwaway pair for hand-run tests.

Calls — STUN and TURN

Calls are peer-to-peer — audio and video flow directly between the two clients, end-to-end encrypted, and never through a relay. STUN and TURN only help the two ends find each other. STUN is free and usually enough; TURN is the fallback for symmetric NATs (common on mobile carriers and corporate networks), where the encrypted media must bounce off a server.

Without a TURN server, calls work in testing and fail for a real share of users on mobile data.
sudo apt install coturn
# then set TURN_URL and TURN_SECRET_FILE in /etc/r2r/relay.env

The relay mints a fresh, expiring credential per client (HMAC of an expiry timestamp) rather than a fixed password, so a leaked credential is worthless within minutes.

Honest caveat. TURN carries the media, so whoever runs it can see both endpoints' IPs and the call's timing and size — never its contents.

Removing your relay

Being easy to leave is part of being trustworthy:

sudo systemctl disable --now r2r-relay
sudo rm /etc/systemd/system/r2r-relay.service /usr/local/bin/r2r-relay
sudo rm -rf /var/lib/r2r /etc/r2r    # deletes stored messages and the node identity
/var/lib/r2r/node.key is the relay's permanent identity. Delete it and a reinstalled node returns as a stranger every peer must re-pin.
